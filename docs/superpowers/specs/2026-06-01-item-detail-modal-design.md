# Item Detail Modal

Clicking any item on the build viewer or generate-build page opens an animated modal showing the item's full stats and lore description. The card image morphs into the modal using React's `<ViewTransition>` shared element transitions (canary channel).

## Data Pipeline

The `generate-slim-data.ts` script produces a second tier of detail JSON files alongside the existing slim data. These files are keyed by item name and contain the full attribute set from the raw source data.

### Detail Files

| File | Key Fields |
|------|------------|
| `weapon-details.json` | `description`, `rarity`, `attackAttributes`, `damage`, `scaling`, `guard`, `statusEffects`, `requirements`, `weight`, `upgradeMaterial`, `isBuffable`, `defaultSkillId` |
| `shield-details.json` | Same shape as weapons |
| `catalyst-details.json` | Same shape as weapons |
| `armor-details.json` | `description`, `rarity`, `absorptions`, `resistances`, `weight` |
| `talisman-details.json` | `description`, `summary`, `rarity`, `effects`, `conflicts`, `weight` |
| `spell-details.json` | `description`, `summary`, `fpCost`, `spCost`, `slotsUsed`, `isHorsebackCastable`, `isWeaponBuff`, `requirements` |
| `ash-details.json` | `armamentCategories`, `defaultAffinity`, `possibleAffinities` |

All detail files live in `src/data/`, are generated by `pnpm generate-data`, and are code-split by Vite (never included in the initial bundle).

### Data Sourcing

Detail data is extracted from the raw source files in `data/base-game/` and `data/dlc/`. The generate script merges base game and DLC items using the same normalization logic as the existing slim pipeline (e.g., DLC category name normalization, alphabetical sorting). Damage/scaling values are taken from the Standard affinity entry.

## Data Loading Strategy

### Prefetch on Mount

When the build viewer or generate-build page mounts, a `useEffect` fires dynamic `import()` calls for all detail files in parallel. These resolve in the background and are cached by the JS module system for the rest of the session.

### useItemDetails Hook

```ts
function useItemDetails(itemName: string, category: ItemCategory): ItemDetails
```

Returns the rich detail object for the given item. If the prefetch has completed (typical case), data is returned synchronously. If not, the hook suspends via React's `use()` hook — a Suspense boundary in the modal catches this and shows a skeleton. The hook always returns `ItemDetails` on successful resolution; the pending state is handled by Suspense, not a null return.

### Caching

Once a dynamic `import()` resolves, the module system caches it. No re-fetching occurs. Detail data stays in memory for the session.

## React Canary & View Transitions

### Version Change

Switch `react` and `react-dom` from `^19.2.6` (stable) to a pinned canary release. Pin to a specific canary version (not a floating `canary` tag) for reproducible builds.

### Shared Element Transition

1. `ItemSlot` wraps its item image in `<ViewTransition name={`item-${slotId}-${itemName}`}>`, where `slotId` is a unique identifier for that slot (e.g., `"right-0"`, `"helm"`, `"talisman-2"`). This prevents collisions when the same item appears in multiple slots.
2. `ItemDetailModal` wraps its header image in `<ViewTransition name={`item-${slotId}-${itemName}`}>` with the same name (the selected item's slotId is passed through).
3. On click, `startTransition(() => setSelectedItem(...))` triggers React's view transition. React detects matching `<ViewTransition>` names being removed (card) and inserted (modal) and morphs between them.
4. On close, the reverse morph animates the modal image back to the card position.

### Animation CSS

- Shared element morph: configured via `::view-transition-old()` and `::view-transition-new()` pseudo-elements.
- Modal backdrop: `<ViewTransition enter="fade-in" exit="fade-out">` wrapper.
- Modal content (lore, stats): separate `<ViewTransition enter="fade-in" exit="fade-out">` with slight delay for a staggered reveal.
- `@media (prefers-reduced-motion)` disables all view transition animations, falling back to instant show/hide.

## Modal Component

### Container

Uses the `<dialog>` element for native accessibility: focus trapping, Escape key handling. Rendered via a portal. The backdrop gets a dark overlay with blur.

### Dismissal

Three paths, all triggering `startTransition` to fire the reverse view transition:

- Click the backdrop overlay
- Click the X button (top-right corner)
- Press Escape

### Layout (Scrolling Single View)

1. **Header** — Item image (shared element, morphs from card), item name (Cinzel font), category label, rarity badge.
2. **Lore** — In-game description text, italic, dimmer color.
3. **Stats** — Content varies by item type:
   - *Weapons/Shields/Catalysts:* Attack power rows, scaling with letter grades (S/A/B/C/D/E derived from numeric values), guard values, status effects.
   - *Armor:* Absorption values (physical, strike, slash, pierce, magic, fire, lightning, holy), resistance values (immunity, robustness, focus, vitality, poise).
   - *Talismans:* Effect descriptions with numeric values, conflicts list.
   - *Spells:* FP cost, stamina cost, slots used, horseback castable flag, weapon/shield buff flag.
   - *Ashes of War:* Compatible weapon categories, default affinity, possible affinities.
4. **Requirements** — Stat requirement badges (STR/DEX/INT/FTH/ARC) and weight.

### Loading State

A Suspense boundary inside the modal shows a skeleton with shimmer animation if detail data hasn't arrived. The header image still morphs in via the view transition immediately; only the lore/stats area shows placeholders.

### Styling

Follows the existing dark/gold theme:

- Category-specific gradient classes (`cat-weapon`, `cat-armor`, etc.) for the image background.
- Gold accent borders and dividers matching `border-gold/10`.
- Cinzel display font for item name, Inter for body text.
- Stat values use `font-variant-numeric: tabular-nums` for alignment.

## ItemSlot Changes

### New Props

- `slotId: string` — unique identifier for this slot position (e.g., `"right-0"`, `"helm"`, `"talisman-2"`), used for ViewTransition name disambiguation.
- `onClick?: () => void` — callback to open the detail modal.

### Behavior

- All three variants (`standard`, `compact`, `talisman`) become clickable when `onClick` is provided.
- `cursor-pointer` and `active:scale-[0.98]` for press feedback.
- Item image wrapped in `<ViewTransition name={`item-${slotId}-${itemName}`}>` using a new `slotId` prop for uniqueness.
- `role="button"`, `tabIndex={0}`, `onKeyDown` handling Enter/Space for keyboard accessibility.

### No Visual Changes

Card appearance stays the same. The existing hover styles already suggest interactivity.

## State Management

Each page that renders `ItemSlot` components manages `selectedItem` state locally. Currently this is `build-viewer.tsx` and `generate-build.tsx`:

```ts
const [selectedItem, setSelectedItem] = useState<{ name: string; category: ItemCategory; slotId: string } | null>(null);
```

- Click: `startTransition(() => setSelectedItem({ name, category }))`
- Close: `startTransition(() => setSelectedItem(null))`

No context providers or global state. The `ItemDetailModal` renders conditionally based on `selectedItem`.

## Browser Support

View Transitions API is supported in Chrome 111+, Edge 111+, Safari 18+, Firefox 134+. Unsupported browsers get no animation — the modal simply appears/disappears, which is an acceptable fallback since the dialog functionality is unaffected.
